# D1 direct-process Server/Client acceptance plan

Status: proposal; real-executable end-to-end acceptance is pending. This plan focuses on running the actual `shaar-server` and `shaar-client` processes with provisioned config and identities, observable readiness, authorization, byte-exact forwarding, concurrency, half-close, reconnect, shutdown, and bounded child cleanup. Existing component/API evidence below is not process-level proof. This is an unmerged worktree snapshot; the combined-branch snapshot is not merged, and the DNS sibling is separate and out of scope.

## Existing source evidence (not D1 process acceptance)

- `docs/direct-only-usage.md` documents the binary CLI/config examples, out-of-band identity provisioning, allowlist format, endpoint output, local TCP forwarding and limits (lines 5–60). It explicitly says real-process acceptance remains pending and component CI is insufficient (lines 62–64).
- Server source loads the configured identity and allowlist before binding, prints `bound=` and `public_key=` after bind, caps active sessions at 32, and uses signal-mode/direct-only semantics (`crates/shaar-server/src/main.rs`, lines 17–18, 30–75). It stops accepting and drains session tasks on shutdown (lines 88–165). These are source mechanisms, not process-observed readiness or bounded-time cleanup proof.
- Client source loads the config and existing identity, binds its local listener, allows one endpoint session and at most 16 stream workers, and uses bounded three-attempt dials; access-denied and peer-mismatch errors are terminal (`crates/shaar-client/src/main.rs`, lines 18–21, 67–90, 132–153). Its coordinator responds to session closure, aborts and joins workers, then closes listener/endpoint on shutdown (`lines 190–255`). These are not yet demonstrated across real child processes.
- Existing public SDK tests establish exact payload echo and target-connection counts, deny/impersonation with zero target accepts, and 16-stream capacity/resource release (`crates/shaar/tests/sdk_network.rs`, lines 69–175 and 177–243). They use in-process endpoint/session APIs, not the actual executable/config/key-provisioning path.
- Server unit modules cover admission, allowlist, runtime and shutdown (`crates/shaar-server/src/tests.rs`, lines 1–11). Client source includes coordinator reconnect tests (`crates/shaar-client/src/main.rs`, lines 306 onward) and separate behavior/admission/task test modules (`lines 273–280`). No inspected evidence showed a D1 harness launching both built binaries as OS child processes.
- Existing main CI is Linux/Windows and runs format, clippy, tests, and structural checks (`.github/workflows/ci.yml`, lines 25–35); the focused SDK-lock workflow runs server/client package tests (`.github/workflows/sdk-lock.yml`, matching grep output around lines 113–119). Those component jobs do not by themselves assert process-level D1 behavior.

## D1 real-process acceptance plan

1. **Build and supervise the real executables in CI.** Add a dedicated D1 harness/job that launches the actual built `shaar-server` and `shaar-client` binaries as child processes, not substitutes, library calls, mocked transports, or test-only forwarding paths. Use isolated temporary directories and loopback-only target/listener ports; capture stdout/stderr and exit status. Pin an overall case deadline and per-transition deadlines. The harness must record child PIDs, wait for expected termination, and on every pass/failure path terminate remaining children, wait/reap them, and assert no child remains. Keep CI matrix/platform claims explicit; begin on supported Linux/Windows runners if the harness can supervise children consistently on both.
2. **Provision identity and config through the documented operator contract.** Generate deterministic test-only 32-byte seed files using an approved test fixture/provisioning path before launch; never ask either binary to generate/export keys. Derive the corresponding client public key for the server's allowlist through a trusted test helper/API and provision the server public key plus numeric reachable `server_address` to the client config. Create ktav files in the case temp directory, use `fallback: signal`, explicit `--config` paths, loopback client listen and loopback server target. Provision identity files as owner-only: on Unix require owner read/write and no group/other access; on Windows require a protected DACL with no inherited ACEs and at least one ALLOW ACE, and every ALLOW ACE must have a nonzero mask and grant access only to the Owner Rights SID (`S-1-3-4`, `OW`); do not grant ALLOW access to the owner-account SID or SYSTEM. DENY ACEs for other principals may coexist. Verify the effective file ACL after creation and before launch; secure config/allowlist/parent directories as needed, noting the file DACL does not protect directory entries. Include deliberately insecure Unix modes and Windows ACLs as negative cases: launch the binary with an insecure key and require the binary itself to reject it before readiness; harness-side rejection before launch does not satisfy this case. If the harness cannot safely provision the case or observe the binary's rejection/readiness boundary, mark that platform's permission evidence unsupported/gapped, not passed. Assert startup failure/nonzero exit and useful diagnostics for missing/malformed key, invalid config, missing allowlist, and invalid address; assert no successful readiness marker on any failure.
3. **Make readiness observable and race-free.** Start the target TCP fixture first, then server, then client. Parse the server's actual `bound=<socket> public_key=<key>` stdout line as readiness, validate it matches the provisioned public key and chosen port, and use that endpoint in client config (or reserve/configure a fixed test port without races). Establish client readiness by bounded connection to its loopback listener plus a successful authenticated transaction—not by a sleep or process-alive check. Verify logs/config do not expose seed bytes. Confirm startup is direct-only; no signaling/data fallback is asserted or implied.
4. **Prove allow/deny and exact target forwarding across processes.** For an authorized client, send unique binary payloads including empty, short, and larger boundary-appropriate values through the client's local TCP port. Target fixture records each accepted connection and exact received bytes; return distinct exact response bytes and assert byte-for-byte equality at the local socket. Assert only expected target connections occur. Run separate negative cases using (a) a non-allowlisted client identity and (b) an authorized client configured with a wrong pinned server key. Before each attempted local connection, establish and record a zero target-accept baseline; continuously monitor the target accept counter from before that attempt through the terminal boundary and child termination/reap, asserting it remains exactly zero throughout. First prove the local listener accepted the attempted connection (the post-admission boundary), then observe the specific terminal denial/peer-mismatch diagnostic and closure/failure of that local stream; record that terminal event and its timestamp as the oracle boundary. A timed period with no target accept, a still-alive process, or a timeout alone is insufficient evidence of denial. If local admission, continuous monitoring, or the terminal outcome cannot be observed, label the oracle unsupported/incomplete and the gap explicitly; do not claim denial.
5. **Exercise concurrency and TCP half-close.** Open the documented maximum 16 concurrent local client streams, associate each with a unique nonce/payload, and assert each reaches the target exactly once with no cross-stream mixing, truncation, duplication, or response corruption. Verify a 17th worker is not admitted beyond the bound and that server admission remains within its 32-session limit in a separately bounded case. For half-close, send request bytes then shutdown only the local write half; the target must observe EOF, still send its complete response, and the local client must receive exact response bytes before EOF. Assert time-bounded completion and no leaked target sockets/workers.
6. **Prove session loss, reconnect, and shutdown.** Force the active server/session to close after an established transaction. Assert the existing stream is not claimed to survive; a subsequent local TCP connection must cause a new bounded direct dial and complete a fresh exact transaction. Verify access-denied/peer-mismatch do not consume retries, while transient dial failures respect the three-attempt timeout/backoff budget. Request graceful shutdown by delivering Ctrl-C to each child through a platform-appropriate mechanism and prove delivery by observing the process's shutdown effects: listener closure, expected exit status, server drain/client worker abort-and-join behavior, closed target sockets, released ports, and child exit/reap. Require these within explicit deadlines. If Ctrl-C delivery cannot be proved on a platform, report shutdown-signal evidence unsupported/gapped; do not substitute an unverified Windows console/process API claim or label forced termination as graceful shutdown. On deadline, escalate termination in a bounded, documented sequence, wait for process exit and reap every child, and fail the case if any child remains; record graceful result separately from escalation. Repeat shutdown at startup/readiness, active stream, and reconnect phases.
7. **Publish separate acceptance evidence and keep transport gates distinct.** CI artifacts should contain redacted case results: executable identity/version, OS, config shape (never secrets), readiness event, target accept counts/payload digests or test-only bytes, denial outcome, concurrency/half-close/reconnect assertions, child PID/exit/reap records, and elapsed times. Require each assertion to fail the job on mismatch or deadline; retain logs with seed/key material scrubbed. Mark D1 accepted only from these real-process CI results; source inspection and in-process tests remain supporting evidence. Keep strict signaling-only/P03 as an explicit independent transport-policy constraint: its decoded-STREAM oracle, positive calibration, pre-direct/post-loss/re-punch coverage remain separately unproven/accepted only by their own evidence. P03 is not a mistaken prerequisite for proving that D1 real executables can connect directly and forward traffic. Keep native Rust Yggdrasil/P07 as a separate, independently authorized gate; it neither proves D1 nor substitutes for P03.

## Constraints and evidence labels

This plan does not claim that any proposed child-process scenario has run. Existing code/tests establish mechanisms at source or component-test scope only. Acceptance must distinguish source inspection, in-process test results, real executable CI observations, and separately authorized manual home/mobile testing. The present direct-only guide says no guaranteed NAT traversal and no Ygg fallback; D1 process acceptance should therefore use a controlled directly reachable loopback CI topology, not claim universal network reachability. Maintain English content and the seven-items-per-directory rule (`CLAUDE.md`, lines 48–60). Revise this document only; do not execute project code, Cargo, tests, network operations, modify external paths, integrate Yggdrasil, or touch the DNS sibling.
