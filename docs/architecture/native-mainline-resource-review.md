### Result-bytes bound (what can and cannot be claimed)

The proposed contract says at most 8 result channels and 32 entries / 65,536 bytes **per operation**. That is a proposed consumer-facing accounting target, not a source-observed bound. N currently uses unbounded channels at `src/dht.rs:265,364,430` and retains response vectors per query (`src/core/iterative_query.rs:24-27,177-184`). The 2048-byte KRPC datagram ceiling constrains each received datagram, not the count of responses to one query, the number/size of decoded response objects, cloning, or channel backlog. A query may hold results until completion while each sender retains a channel; no source fact supports “maximum 32 entries” or “65,536 bytes” today.

The proposal's output shape is 32 entries of at most one full signed record each (1104 bytes), so the dominated per-operation payload bound is **32×1104 = 35,328 logical signed-record bytes**, below the separate 65,536-byte ceiling. For eight simultaneously charged operations this is **8×35,328 = 282,624 logical record bytes**. For this shape the 65,536-byte check is not the tighter independently reachable limit; it remains a separate proposed ceiling, not an additional 65,536 bytes to add to the result budget. This calculation assumes every entry is bounded by the full-record maximum and the 32-entry limit is enforced. It counts logical record bytes only—not RSS, collection/channel overhead, spare capacity, parser/decoder temporary representations, clones/fanout copies, or N query storage. Those need separate ownership charges; the current unbounded source channels and response vectors provide no observed such limit. Avoid interpreting either number as total process memory.

### Rollback, cancellation, and closure obligations

1. **Reservation transaction:** allocate logical operation/query/RPC/outbox/result charges before retaining owned bytes or enqueueing. On serialization failure, queue rejection, socket-send error, timeout, late response, cancellation and shutdown, remove/release exactly the reservation actually acquired. For N request path, transaction ID is inserted before encode and encode failure swallowed (`actor/socket.rs:220-233`); a repair must return failure and roll back. For direct datagram send, reject oversize and reserve before message enters actor inbox, then carry charge through outbox and awaited socket send (`dht.rs:199-211`, `actor.rs:443-445`, socket `:261-272`).
2. **Shared target:** deduplication creates one underlying iterative query but vectors retain arbitrarily many GET/PUT waiters (`actor.rs:32-34,426-435`). Caller cancellation must unlink that waiter; only cancel shared underlying query when no live waiter/owner requires it. Completion must not send/cache/dial for a cancelled requester. Count query once and each per-waiter response/channel/backlog separately. Cancellation cannot simply decrement a semaphore while the query or queued sends remain.
3. **Maintenance and internal paths:** tick visits and periodic refresh/pings, bootstrap, referral-triggered populate, query-completion ping, PUT continuation, inbound response replies, and explicit datagram bypass all share the same budgets. Requests rejected on caller-facing boundary cannot be used to infer those paths absent.
4. **Outbox and in-flight send:** `flush` pops before awaiting network send (`socket.rs:261-268`). Keep a separate send-in-progress charge through send completion and failure cleanup; stop/abort must not report success or release ownership while that future still retains bytes/socket.
5. **Actor close:** accepted plan requires retained real actor join handle, out-of-band stop independent of flush/receive, and observed join/socket destruction before success. Source currently drops join handle (`dht.rs:139-143`) and flush precedes stop-message select (`actor.rs:402-449`). An SDK wrapper task or timeout around a caller is not proof dependency work stopped. If stop/join cannot be exported, SDK facade cannot guarantee close/charge release.

## Bencode, signed-record parsing, UDP truncation

- **Observed SOURCE:** N `src/actor/socket.rs:280-305` allocates fixed `[u8; 2048]`, obtains `(amt, address)` from socket layer, slices `[..amt]`, and invokes `Message::from_bytes`. N `src/common/messages.rs:722-730` rejects fewer than 15 bytes or a non-`d` first byte, then calls `internal::DHTMessage::from_bytes`; `src/common/messages/internal.rs:26-34` delegates directly to `serde_bencode::from_bytes` and serializes via `serde_bencode::to_bytes`. N manifest `Cargo.toml:82-96` declares `noq-udp 1.0.0`, `serde 1` with derive, `serde_bencode 0.2`, and `serde_bytes 0.11.15`; these declarations do not expose parser limits or internals.
- **Observed SOURCE:** parser model `src/common/messages/internal.rs:4-23,37-149` uses transaction ID `Vec<u8>`, `String` error description, flattened top-level variant, internally tagged request/message enums, and an untagged response enum explicitly order-sensitive. Byte fields include `Box<[u8]>`, `Option<Box<[u8]>>`, and peer `Vec<ByteBuf>` (`:177-244` and subsequent argument structs); records are converted into product response fields in `src/common/messages.rs:490-715`. Bencoded compact node bytes are converted with `Vec::with_capacity(bytes.len()/26)`, per-node `Node` construction, then boxed (`:835-866`); compact-byte-length divisibility is checked, but no maximum node count is checked there. Peer byte buffers are traversed and collected into `Vec` (`:868-889`). This is evidence of potentially multiplicative live representations during decode/conversion, not measured allocation amplification.
- **Observed SOURCE:** `Node` contains `Arc<NodeInner>` with optional `Box<[u8]>` token (`src/common/node.rs:17-38`); `token()` clones that box (`:93-96`). Node wrapper clones share the `Arc<NodeInner>` and therefore its optional token allocation (`src/common/node.rs:17-38`); calling `token()` separately clones the token `Box` bytes (`:93-96`).
- **Parser behavior not established:** the `serde_bencode` implementation is absent from N source; neither its recursion/default depth, string/collection length limits, trailing-byte handling, duplicate-key semantics, nor proportional-allocation behavior can be asserted from these call sites or manifest declarations. Likewise `serde_bytes` and derive behavior are not a bound. Do not acquire transitive parser source for this review.
- **UDP inference/unresolved:** `UdpIo::try_recv` returns `meta[0].len` without exposing a truncation flag (`src/actor/socket.rs:95-108`); wrapper slices the fixed buffer using that length (`:280-285`). If the dependency reports `len > buf.len()`, that slice would panic; whether it can is unresolved because `noq-udp` implementation and syscall semantics are absent. Alternatively, if the receive layer clamps the length, a truncated valid-looking prefix may reach `Message::from_bytes`; if it returns an I/O error, the actor logs it and does not parse that datagram (`:359-361`). Which behavior occurs is unknown. The wrapper itself has no explicit truncation signal; this does not establish the underlying syscall behavior.
- **Observed SOURCE / conditional defect inference:** `src/common/messages.rs:891-906` checks only whether a signed-peer byte string length is a multiple of 104, then unconditionally slices `[32..40]`, `[0..32]`, and `[40..104]`. Empty input passes the modulo check and would panic at the first slice if it reaches this converter; a length greater than 104 but divisible by 104 decodes only the first 104 bytes and ignores the remainder. `bytes_to_signed_peers` maps this converter over the `Vec<ByteBuf>` (`:882-889`), called for response conversion (`:648-657`). This is a source-level conditional defect observation, not a claim about exploitability, parser reachability, or executed behavior. Regression belongs in `messages.rs` existing private test module (`:974` onward): empty and multi-record lengths must return an error or be handled per an explicitly reviewed contract without panic or silent discard.
- **Observed SOURCE:** mutable item construction/verification in `src/common/mutable.rs:80-108` takes owned boxed value and verifies `encode_signable(seq, &v, salt)`; `encode_signable` allocates a `Vec`, formats framing, appends the complete value, then boxes the result (`:145-156`). No 1000-byte guard appears in this path. Therefore a packet-size acceptance limit applied only later would not prevent this verification temporary allocation; enforce payload length before decode/verification at its owner.
- **Observed SOURCE:** accepted contract states DNS payload ≤1000, full signed packet ≤1104 and N receive buffer 2048. These bytes bound wire/payload policy only; they do not prove parser allocation/depth, item counts, or checked decoding before allocation. Minimum review obligation is receive-truncation semantics plus parser-supported depth/length/allocation controls (or an enforceably bounded decode surface); test deep/high-item/malformed/truncated packets at owning N test modules. Without evidence, parsing resource safety remains unresolved.

## Determination

**Inference — structural feasibility only, not parser-safety evidence:** N's owning boundaries could structurally enforce aggregate quotas via narrow dependency-private controls; that does not establish parser safety or prove all proposed limits feasible. The current SDK-facing surface alone cannot enforce them, and parser/dependency behavior blocks a complete claim. A shared 256-node aggregate may force cache disablement and may cause ordinary queries or maintenance to stop on exhaustion; this review does not claim normal lookup behavior or full DHT traversal under those ceilings. #247 implementation remains sequenced after #246 specification/tests and parent acceptance as stated in the accepted runtime plan; this review neither reads nor relies on pending sibling drafts. Registry equivalence, parser internals, truncation signal, feasible byte accounting and regression execution remain unresolved.

No implementation, tests, build, Cargo, formatting, lint, metadata, Python/project preparation, network, CI, or DATA execution was performed. This is documentation-only and makes no readiness or test-pass claim.
