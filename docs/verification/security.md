# План проверки безопасности Sha'ar Stack v1

Статус: **реализации нет — пройденных проверок нет.** Каждый контроль ниже — обязательство
с наблюдаемым результатом. Ссылки на инварианты — И1…И10 из
`docs/architecture/threat-model.md`. Оракул — всегда внешнее наблюдение (лог с кодом
отказа, счётчик подключений, инспекция сетевого пути, метрики ресурсов); «тест тестирует
собственную константу» и mock-success оракулы запрещены.

Этапы: **CI-юнит**, **CI-интеграция**, **P03** (блокирующий эксперимент custom transport),
**NAT-стенд**, **ручной стенд**.

## Аутентификация и доступ

**SEC-AUTH-01 — подмена сервера** (И5 смежн., known-key §5)
- Шаги: клиент подключается к endpoint, выдающему себя за сервер, с другим ключом
  (валидный самоподписанный, не pinned).
- Ожидаемо: ошибка *known-key* верификации **до отправки любых прикладных данных**.
- Oracle: код отказа known-key и ноль STREAM по decoded-frames oracle из раздела
  SEC-PATH до отказа. Зашифрованного capture недостаточно. Этап: CI-интеграция.

**SEC-AUTH-02 — неразрешённый клиент** (И1)
- Шаги: неизвестный ключ подключается к серверу.
- Ожидаемо: отказ аутентификации; target не получил ни одного TCP-подключения.
- Oracle: счётчик подключений на тестовом target == 0; лог с кодом отказа allowlist.
  Этап: CI-интеграция.

**SEC-AUTH-03 — авторизованный клиент** (И1, positive control)
- Шаги: ключ из allowlist подключается и передаёт данные.
- Ожидаемо: ровно одно TCP-подключение к target после проверки ключа; данные доставлены.
- Oracle: счётчик target, эхо-данные. Этап: CI-интеграция.

## DHT и недоверенные кадры

**SEC-DHT-01 — повреждённая подпись pkarr** (И6)
- Шаги: запись в тестовом DHT с битой подписью.
- Ожидаемо: запись отброшена; без паники; соединение к адресу записи не открывается.
- Oracle: счётчик отклонённых; отсутствие исходящих соединений. Этап: CI-юнит.

**SEC-DHT-02 — пределы размера и malformed-кадры; фрагментация потока** (И6, И8)
- Positive: (a) кадр/датаграмма ровно максимальной допустимой длины соответствующего слоя
  проходит полностью и совпадает побайтно (положительный контроль границы); (b) кадры,
  приходящие частичными reads/writes (корректная фрагментация транспортного потока),
  валидны и корректно собираются.
- Negative: MTU+1 (сверх допустимого максимума), overflow длины, объявленная длина больше
  фактически полученного количества байт, обрыв в заголовке/перед длиной — отклоняются
  без desync и без неограниченного выделения памяти. Нулевая длина — по требованию
  протокола (QUIC-пакет не может быть пустым), а не как универсальное «любой нулевой
  буфер в любом вызове — ошибка» без контракта. Верхняя граница датаграммы (MTU-путь)
  и допустимая длина кадров приложения не обязаны быть одним числом — проверяется
  согласованный лимит соответствующего слоя.
- pkarr: запись сверх бюджета (предел — контракт, подтверждаемый P01, применяется по
  фактическому бюджету структуры/поля и overhead записи) отбрасывается.
- Ожидаемо: отброс по границе размера/валидности; bounded-буфер; фрагментированный
  валидный кадр и кадр максимальной длины доставляются целиком, побайтно.
- Oracle: метрика пика памяти; лог отказа; побайтное совпадение доставленного на
  границе и фрагментированного. Этап: CI-юнит.

**SEC-DHT-03 — replay устаревшей записи** (И6)
- Шаги: повтор валидной, но устаревшей подписанной записи (старый timestamp/seq).
- Ожидаемо: отклонена как несвежая; свежая запись того же ключа принимается.
- Oracle: счётчик принятых/отклонённых. Этап: CI-юнит.

**SEC-DHT-04 — отказ DHT** (И7)
- Шаги: DHT недоступен/возвращает мусор при старте и в работе.
- Ожидаемо: деградация (нет адреса), не паника; ограниченный retry с backoff.
- Oracle: конечное число попыток в логе; процесс жив. Этап: CI-интеграция.

## Конфигурация и секреты

**SEC-CFG-01 — malformed ktav-конфиг** (И2)
- Шаги: каждый класс некорректности (неизвестное поле, нелокальный target, внешний
  listen, отсутствующий allowlist).
- Ожидаемо: отказ **до старта сети** (ни одного сокета), сообщение указывает поле.
- Oracle: exit-код/лог до открытия портов (netstat/счётчик сокетов). Этап: CI-юнит.

**SEC-CFG-04 — корректный ktav-конфиг: успешный запуск до сквозного эха** (И2, positive
control)
- Шаги: CI-интеграционный прогон — корректный ktav 0.8-конфиг с тестовыми ключами/
  allowlist (синтаксис ktav 0.8.*, без изобретения полей), управляемые endpoint и target;
  client listener реально принимает локальный TCP-коннект; разрешённый клиент отправляет
  известный payload; target получает его и возвращает ответ; клиент получает точные байты
  обратно.
- Ожидаемо: сквозное эхо payload; парсерный unit-тест остаётся отдельным более узким
  контролем и не заменяет этот — наличие открытого сокета или лога старта отдельно
  недостаточно.
- Oracle: точные байты payload на target и на клиенте (эхо); реальное TCP-подключение на
  listener. Этап: CI-интеграция.

**SEC-CFG-02 — секреты не в логах** (И4)
- Шаги: негативные прогоны (SEC-CFG-01, SEC-AUTH-01, SEC-FFI-04) с Debug-логами на
  максимум.
- Ожидаемо: ни seed, ни приватных ключей, ни hex/base64-фрагментов секрета.
- Oracle: grep артефактов CI на известные байтовые/hex-представления секрета.
  Этап: CI-юнит + контроль артефактов.

**SEC-KEY-01 — атомарность create_new; загрузка existing** (И3)
- Шаги: (a) create_new при существующем файле; (b) два конкурентных create_new;
  (c) штатный запуск с существующим корректным ключом.
- Ожидаемо: (a) отказ без изменения файла; (b) ровно один успех; (c) ключ **читается и
  загружается**, файл не меняется — повторный штатный запуск не отвергается. Отказ
  требуется только при попытке создать поверх существующего и при конкурентном создании.
- Oracle: содержимое/inode файла неизменно в (a); результат (b) — одна ошибка;
  (c) успешная загрузка + отсутствие записи в файл. Этап: CI-юнит.

**SEC-KEY-02 — права на файл ключа при создании** (И4)
- Шаги: создание файла ключа на Unix и Windows; в тестовой сборке — контролируемая пауза
  между open и первой записью.
- Ожидаемо: Unix — mode 0600 задан при создании (O_EXCL с mode / umask) без окна
  create→write→chmod; Windows — ACL, ограничивающий доступ владельцем, при создании;
  попытка чтения другим непривилегированным principal в паузе и после записи не даёт
  доступ. Явно: абсолютная защита от root/admin/компрометации ОС не обещается (§3
  threat-model, out of scope).
- Oracle: stat/ACL сразу после создания; результат негативной попытки чтения другим
  principal в тестовой сборке. Этап: CI-юнит (per-OS job).

**SEC-KEY-03 — отсутствие секрета в Debug** (И4)
- Шаги: `format!("{:?}", …)`/Display всех ключевых типов в тесте.
- Ожидаемо: redacted-представление, не байты/hex секрета.
- Oracle: grep вывода на представление секрета. Этап: CI-юнит.

## Concurrency, ресурсы, жизненный цикл

**SEC-CONC-01 — half-close в обе стороны** (И8)
- Шаги: (a) клиент отправляет запрос и выполняет shutdown(write side) — target получает
  EOF и продолжает отдавать ответ; весь ответ до EOF доходит обратно; (b) отдельный
  сценарий: target первым отправляет ответ/часть данных и делает shutdown своей
  write-стороны; клиент видит EOF на чтении, но **затем продолжает писать** в своё
  TCP-направление; target продолжает читать и получает все последующие байты до EOF
  клиента. Цель (b): ловит преждевременное закрытие оставшейся половины соединения при
  получении FIN со стороны target — «сервер выполнил shutdown» сам по себе недостаточно.
  (c) разрыв клиента в середине передачи; (d) shutdown сервера при активных сессиях.
- Ожидаемо: оба направления (клиент→сервер half-close и сервер→клиент half-close)
  проверяются отдельными прогонами; QUIC FIN переносится корректно в каждом направлении;
  все задачи завершаются, дескрипторы возвращаются, shutdown без зависаний.
- Oracle: счётчики задач/фд до и после == базовым; полученный EOF и полный ответ/продолжение
  записи на противоположной стороне; timeout-test на «нет зависаний». Этап: CI-интеграция.

**SEC-CONC-02 — изоляция потоков при reset/timeout** (И8)
- Шаги: один QUIC-поток сессии получает reset/timeout.
- Ожидаемо: соседние активные потоки той же QUIC-сессии продолжают работать и не
  закрываются; сбой изолирован в пределах потока.
- Oracle: данные по соседним потокам доставляются после сбоя; лог с кодом отказа только
  затронутого потока. Этап: CI-интеграция.

**SEC-RES-01 — медленный клиент** (И8)
- Шаги: клиент читает с искусственной задержкой / не читает вовсе, несколько таких.
- Ожидаемо: bounded очереди, stage-deadline, отказ соединения вместо роста памяти.
- Oracle: RSS/буферы bounded; новые соединения получают явный отказ, не молчание.
  Этап: CI-интеграция.

**SEC-RES-02 — шторм подключений/стримов** (И8)
- Шаги: превышение лимита connections/streams.
- Ожидаемо: отказ сверх лимита, существующие сессии не затронуты.
- Oracle: счётчики admissions, ошибки лимита в логе. Этап: CI-интеграция.

**SEC-RES-03 — slowloris против абсолютных дедлайнов** (И8)
- Шаги: клиент передаёт по одному байту перед каждым idle timeout, удерживая
  handshake/frame-фазу.
- Ожидаемо: активность не продлевает **абсолютный** handshake/frame deadline — соединение
  обрывается по абсолютному сроку независимо от трафика.
- Oracle: время жизни соединения ≤ абсолютному дедлайну; лог с кодом отказа по дедлайну.
  Явно: SEC-RES-01 (один медленно читающий клиент) это не доказывает.
  Этап: CI-интеграция.

**SEC-FAIL-01 — отказ relay/Ygg-пути** (И7)
- Шаги: инъекция отказа Ygg-пути и relay в каждой фазе (до direct, при работе), включая
  дропы/задержки/мусор от релея.
- Ожидаемо: деградация пути, ограниченный retry с backoff, без паники и роста памяти.
- Oracle: лог попыток (конечное число), метрики ресурсов. Этап: CI-интеграция.

## Путь данных (P03 — блокирующий эксперимент)

Общее для SEC-PATH-01/02/03: oracle — *decoded-frames oracle*: декодированные QUIC-кадры
с однозначной привязкой к фактическому egress path/transport (test-only hook до шифрования
с path metadata, либо test-only keylog + capture + доказуемое декодирование). Наблюдение
зашифрованных пакетов и маршрута STREAM от CRYPTO/ACK/согласования не различает и
самостоятельным оракулом не является. Доступность hook/keylog в выбранной версии iroh —
условие, которое подтверждает P03; её существование не утверждается. Калибровка
чувствительности обязательна: положительный контроль — заведомо разрешённый STREAM через
custom-путь должен фиксироваться как нарушение; нулевой результат без калибровки — не
доказательство. Каждый контроль прогоняется во всех трёх фазах (до direct, при отказе,
после reconnect) и обоих режимах (signal/standby); app-level недоставка данных не
доказывает отсутствие STREAM на wire. При недостаточном oracle P03 по И5 остаётся
**не пройденным** (gate).

**SEC-PATH-01 — relay до direct** (И5)
- Шаги: фаза установления до появления direct-пути; прокачка прикладных данных;
  прогон в режимах signal и standby.
- Ожидаемо: декодированные кадры по signaling-пути — только signaling (кандидаты/
  согласование), ноль STREAM; калибровочный STREAM на custom-путь фиксируется.
- Oracle: decoded-frames oracle (см. выше), привязка кадров к egress path. Этап: P03.

**SEC-PATH-02 — relay при отказе direct** (И5)
- Шаги: разрыв direct-пути в активной сессии (фейк-инъекция); прогон в signal/standby.
- Ожидаемо: сессия переходит на Ygg standby или рвётся; ноль STREAM через relay.
- Oracle: decoded-frames oracle по фактическому egress path. Этап: P03.

**SEC-PATH-03 — relay после reconnect** (И5)
- Шаги: восстановление после разрыва; все подфазы reconnect; прогон в signal/standby.
- Ожидаемо: signaling-only инвариант сохраняется во всех подфазах reconnect; Ygg в
  режиме `signal` — тоже только сигнализация.
- Oracle: decoded-frames oracle. Этап: P03 + NAT-стенд.

## FFI-граница yggdrasil-go

**SEC-FFI-01 — double start и частичный failure старта** (И9)
- Шаги: повторный вызов start при работающем ядре; старт нескольких ресурсов, где один
  падает посреди.
- Ожидаемо: явная ошибка, состояние не повреждено; частичный failure завершается полным
  cleanup уже созданных ресурсов (ни одного утечка/полуживого ресурса).
- Oracle: код ошибки, работоспособность после, счётчики ресурсов == базовым.
  Этап: CI-интеграция.

**SEC-FFI-02 — stop без зависаний и shutdown-циклы** (И9)
- Шаги: stop при активном блокирующем recv; повторные циклы start/stop; конкурентные
  stop/send/recv.
- Ожидаемо: join завершается, потоки завершены, ресурсы освобождены; циклы устойчивы.
- Oracle: счётчики потоков/фд до/после; timeout на join. Этап: CI-интеграция + FFI-стенд.

**SEC-FFI-03 — конкурентные send/recv и граничные параметры** (И9)
- Шаги: параллельные send/recv из нескольких задач; вызовы с граничными длинами:
  MTU (валидная граница — должна проходить), MTU+1 и значения, дающие overflow длины
  (отрицательные); нулевая длина — по контракту ABI/протокола, не универсально;
  stale/unknown handle.
- Ожидаемо: safe API отвергает некорректные состояния/размеры **до** FFI-вызова
  (валидация на уровне обёртки; заведомо dangling/невалидные указатели в foreign-код не
  подаются); без UB/дедлоков.
- Oracle: коды отказа на границе; stress-цикл под debug-assertions, счётчики ресурсов
  стабильны (счётчики/debug asserts UB не доказывают — см. И9, уровни проверки).
  Этап: FFI-стенд.

**SEC-FFI-04 — panic containment с ограничениями** (И9)
- Шаги: индуцированная паника в Go-колбеке и в Rust-обёртке — только там, где реально
  применяется unwind+recover (catch_unwind / recover()).
- Ожидаемо: паника преобразована в код ошибки ABI там, где recover настроен; **abort не
  ловится магически**; процесс может требовать fail-closed (документированный shutdown
  вместо «всегда выживает») — «процесс всегда выживает» не обещается.
- Oracle: лог с кодом ошибки в recover-конфигурации; поведение при abort соответствует
  задокументированному fail-closed. Этап: FFI-стенд.

**SEC-FFI-05 — уровни проверки границы** (И9)
- Шаги: (a) статический SAFETY/ownership/cgo-contract review всех unsafe-участков;
  (b) Miri там, где работает без исполнения foreign-кода; (c) sanitizer/FFI-прогон в CI
  (ASan/UBSan/valgrind, где применимо).
- Ожидаемо: ни один уровень не подменяет другой; ограничения каждого зафиксированы:
  (a) покрывает только прочитанный код и не исполняется; (b) foreign-часть не выполняется;
  (c) ограничения платформ/инструментов задокументированы.
- Oracle: отчёты каждого уровня в артефактах CI/стенда. Этап: P01/P07 review + CI.

## Supply-chain и CI (P02+)

**SEC-SUP-01 — зависимости: pin/происхождение/лицензии** (И10)
- Шаги: независимая проверка lock-файла, источников (registry/git URL/rev) и лицензий
  против списка допустимых.
- Ожидаемо: всё зафиксировано и соответствует списку; расхождение — отказ сборки.
- Oracle: отчёт проверки в артефактах CI. Явно: pin ≠ security proof — pinning сужает
  поверхность, не заменяет проверку. Этап: CI (P02+).

**SEC-SUP-02 — минимальные permissions workflow** (И10)
- Шаги: YAML-проверка всех workflow-файлов: top-level `permissions: { contents: read }`,
  повышение прав только там, где необходимо; действия без избыточных прав.
- Ожидаемо: все файлы соответствуют; иное — отказ CI.
- Oracle: результат линтера/проверки в CI. Этап: CI (P02+).

**SEC-SUP-03 — secret/cache boundary и fork PR** (И10)
- Шаги: инспекция workflow: отсутствие secret env в build/cache-producing steps;
  trust boundaries для fork PR (секреты/окружение недоступны fork-ранам).
- Ожидаемо: ни один cache-producing step не получает secret env; fork PR не имеет доступа
  к секретам.
- Oracle: статическая проверка workflow-файлов в CI; отчёт в артефактах.
  Этап: CI (P02+).

## Loopback-инварианты

**SEC-LOOP-01 — нелокальный target** (И2, И1)
- Шаги: конфиг с target вне 127.0.0.1.
- Ожидаемо: отказ валидации до сети.
- Oracle: лог отказа до сокетов. Этап: CI-юнит.

**SEC-LOOP-02 — нелокальный client listener** (И2)
- Шаги: конфиг с listen не на loopback.
- Ожидаемо: отказ валидации до сети.
- Oracle: лог отказа до сокетов. Этап: CI-юнит.

## Что требует реального стенда и не проверяется юнит-тестом
